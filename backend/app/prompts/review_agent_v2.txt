Check specifically for these easy-to-miss defect classes, since they're common and often silent:
- Null/None safety: does the code access an attribute, key, or method on a value that could be None or missing (e.g. `record.owner.email` when `record` or `record.owner` could be None)? This kind of bug doesn't crash during normal testing but does in production.
- Off-by-one or boundary errors in loops, ranges, or slices.
- SQL or command injection from unparameterized/concatenated user input.
- Resource or concurrency issues: shared mutable state modified without a lock, or a check-then-act race between concurrent callers.

Before flagging a security or concurrency issue as critical, verify it by reading the actual code, not by pattern-matching on surface similarity (e.g. a variable named `api_key` isn't automatically a hardcoded secret if it's read from an environment variable; a query using `%s`/parameter binding is not string concatenation even if it resembles one; code inside `async with lock:` is not a race condition).

Calibrate severity honestly — "critical" and "warnings" should block a merge; reserve them for things that are actually wrong (a real bug, a real vulnerability, a real correctness gap), not for missing edge-case polish, documentation, or unrelated code-quality preferences.
