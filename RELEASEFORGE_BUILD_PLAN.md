# ReleaseForge AI — Build Plan

This is the working plan for turning [`ReleaseForge_AI_Complete_Project_Design.md`](./ReleaseForge_AI_Complete_Project_Design.md) — the full 15-agent, MCP/RAG/knowledge-graph, cloud-native vision — into something actually built, incrementally, in a way that's meant to teach the concepts along the way rather than just produce a working system.

The design doc is the source of truth for **what** the finished platform covers. This document is the source of truth for **in what order** we build it, and **why** that order isn't the doc's own Stage 1–16 sequence.

---

## Why not build it in the doc's original order

The doc's roadmap builds MCP integrations (Stage 2) and the LangGraph workflow (Stage 3) before there's a single agent that does anything useful (Stage 4+). That's backwards for both engineering risk and learning: it sinks time into plumbing before validating that the core loop works at all.

Instead, this plan follows one rule: **build a thin vertical slice end-to-end first, then widen it.** Get one path — Planner → Coding → Test → PR — working with the crudest possible tools (direct filesystem + git calls, no MCP) before adding review, deployment, monitoring, memory, RAG, or a knowledge graph. Every later phase either widens that working core or retrofits proper infrastructure (like MCP) around tools that already exist and are already understood.

Every item in the design doc's Section 22 concept checklist still gets built — just in an order where each phase produces something real that the next phase actually depends on.

---

## Architecture

```
VS Code Extension (TypeScript, thin client)
        |  reads the active workspace folder as the target repo
        |  localhost HTTP (configurable via releaseforge.backendUrl)
        v
ReleaseForge AI Core (Python: FastAPI + LangGraph — the agent brain)
        |
        v
LLM Provider  (Ollama now -> OpenAI / Anthropic later, same interface)
        |
        v
MCP Client (backend/app/mcp/client.py)
        |  one MCP handshake per server, tool discovery via each server's real list_tools()
   +----+----+-------------+
   v         v             v
Filesystem  Docker    Kubernetes
MCP server  MCP server  MCP server      (each its own subprocess — real multi-server
   |            |            |           orchestration, not simulated)
   v            v            v
 git/gh     docker CLI   kind/kubectl
```

**Why a VS Code extension instead of a web app:** `vscode.workspace.workspaceFolders` gives the active repo path for free — no manual "point it at a repo" config. VS Code's native UI (diff viewer, Quick Pick, notifications, output channels) covers most of the design doc's human-in-the-loop needs (Section 13) without building a custom React frontend.

**Why the agent brain is a separate Python process, not TypeScript in the extension itself:** LangGraph, the official MCP SDK, LlamaIndex, and the Neo4j driver are all Python-first and meaningfully more mature than their JS equivalents. The extension stays a thin client — UI plus "here's the repo, here's the request" — and the FastAPI/LangGraph service does the actual orchestration.

**LLM provider strategy:** `backend/app/llm/base.py` defines one `LLMProvider` interface. The Ollama adapter (`ollama_provider.py`) is built on the `openai` Python SDK pointed at Ollama's OpenAI-compatible endpoint (`http://localhost:11434/v1`) rather than a bespoke Ollama client — so adding real OpenAI later is a different `base_url` / `api_key` / model name, not a rewrite. An Anthropic adapter needs its own implementation (different message format) but slots into the same interface. Selection happens via `RELEASEFORGE_LLM_PROVIDER` in `backend/app/llm/factory.py`.

## Phase Plan

### Phase 0 — Scaffolding — **done**
`extension/` (TypeScript, compiles, one command that pings the backend) and `backend/` (FastAPI + the `LLMProvider` interface + Ollama adapter). Verified end-to-end: extension command → backend → Ollama → response.

**Pulled forward from Phase 10:** a real sidebar chat UI (VS Code webview view, themed to match the editor) so the extension is actually usable against any open repo instead of a single diagnostic command. Shows the active repo name, sends conversation history to a new `/chat` backend endpoint, and is explicit in its system prompt that it can't read or change files yet — that's still Phase 1. This is the interaction surface Phase 1's agent graph plugs into next; the UI shell existing first means each later phase adds capability behind an already-working interface instead of building UI and agent logic at the same time.

### Phase 1 — Vertical slice: Planner → Coding → Test → PR — **done**
One LangGraph graph (`backend/app/agents/graph.py`), driven entirely through the Phase 0 chat panel — no new UI needed. No MCP, no review agent, no deployment: file edits and git calls are plain Python/subprocess, on purpose (Phase 7 wraps them in MCP later, once they're understood).

Flow: `classify_intent` (LLM: is this a repo task or just conversation?) → `plan` (LLM: pick one target file + describe the change, as JSON) → `code` (LLM: write the file's full new contents, written to disk immediately) → `test` (detects and runs pytest/`npm test`/Django, no LLM) → `await_approval` — a real LangGraph `interrupt()`, pausing the graph and returning plan + test result to the chat panel — → `create_pr` (only on resume; git checkout/add/commit/push, then `gh pr create` or a compare-URL fallback).

Verified against a disposable scratch repo (never the real project repo): chit-chat correctly stayed conversational; a task request produced a correct file edit that passed its real pytest suite; approving triggered a real branch/commit and a graceful, clearly-reported failure on `git push` (no remote on the scratch repo — the failure path itself was the thing being tested); declining left the edit on disk, uncommitted, with no git side effects at all.

Deliberately out of scope here (arrives in later phases): no re-planning if tests fail — Phase 1 just reports failure and still asks for approval, since the fix-and-retry loop is Phase 2's reflection pattern; no multi-file changes; no conversation memory beyond the single pending approval (Phase 5).

**Also pulled forward from Phase 10:** the extension is now installed as a persistent VS Code extension (`vsce package` + `code --install-extension`, wrapped in a one-line `npm run release`) instead of only running via F5's Extension Development Host, and it auto-starts the backend itself (`extension/src/backendManager.ts`) — checks `/health`, spawns `uvicorn` if it isn't up, prompts once (folder picker) to locate the backend if unconfigured, then remembers the location in *user* (not workspace) settings so an untrusted repo's `.vscode/settings.json` can't redirect which Python binary gets launched.

### Phase 2 — Independent Review Agent + reflection loop — **done**
A `review` node sits between `test` and `await_approval` (`backend/app/agents/graph.py`). It's a separate LLM call with its own skeptical-reviewer prompt — not the Coding Agent grading its own work — that judges the diff against the request, factors in the real test result, and returns `APPROVED` or `CHANGES_REQUESTED` with critical/warning/suggestion feedback and a risk level, mirroring the design doc's Section 3.4 review-report format.

On `CHANGES_REQUESTED`, the graph routes back to `code` with the reviewer's feedback appended to the prompt, then re-tests and re-reviews — the reflection loop from Section 12. This is capped at `MAX_REVIEW_ROUNDS = 2` so a stuck local model can't loop forever; after the cap, it still surfaces everything (failing tests, the review's critical feedback, risk level) in the approval prompt instead of quietly proceeding as if nothing were wrong. The review is explicitly instructed to request changes whenever the real test result is FAILED, rather than trusting the model's own read of the diff for that call.

Verified against a fresh scratch repo: a normal request produced `APPROVED (risk: Low)` on the first pass; a deliberately broken request (rewriting `add` to multiply) produced a failing test, a `CHANGES_REQUESTED` verdict, a real loop back to `code`, a second failed attempt, and a correct stop at the round cap with the failure fully visible in the approval prompt — the small local model could not self-correct even with explicit feedback, which is a real, documented limitation rather than a bug to paper over. Declining after that left the repo untouched, as expected.

**Real-world bug found and fixed, same day:** a live request against an actual project ("add a field email in login page located in public folder") landed the change in a `login.html` at the repo root instead of the real `public/login.html` — the Planner's JSON output dropped the folder. Two fixes, both verified against a scratch repo reproducing the exact scenario:

1. **A deterministic correction, not just a prompt tweak** — `_resolve_target_file()` in `graph.py`: if the model's `target_file` doesn't match any real file but exactly one file in the repo shares that basename, the real path is used instead of the guess. Ambiguous or genuinely-new files are left alone. The Planner prompt was also tightened ("copy the path EXACTLY as shown, don't shorten it"), but the deterministic check is the part that actually can't fail silently.
2. **Also pulled forward from Phase 10: a real diff view.** The chat panel never showed *what* changed — only a text summary — so a wrong-file mistake was invisible until someone went and checked by hand. `/chat` now returns the target file plus its before/after content whenever a task reaches an approval step (`backend/app/main.py`), and the extension opens VS Code's native diff editor automatically (`extension/src/diffProvider.ts`, a `TextDocumentContentProvider` serving the "before" version as a virtual read-only document, since only the "after" version exists as a real file on disk by that point). You now see the exact change, file path included, before ever being asked to approve anything.

**Same bug, new shape, found later on a real Vue.js project:** a request to change the login page targeted `src/views/login.html` — a file that shouldn't exist in a Vue project at all — instead of the real `src/views/login.vue`, because the two don't share a basename and the original fix only matched on exact filename. `_resolve_target_file()` now tries a second, still-unambiguous correction: same directory, same filename stem, different extension — catching a framework mismatch (asked to edit `.html` when the project's real files are `.vue`) the same way the first fix caught a dropped folder. It stays deliberately conservative: if more than one file shares that stem (e.g. `login.vue` and `login.jsx` both existed), nothing gets auto-corrected — an ambiguous guess is left exactly as the model made it, same principle as before. Verified with direct unit tests (no LLM needed, since the function is pure logic): the exact reported case resolves correctly, a genuinely ambiguous case is correctly left unresolved, and a real new-file case is correctly left untouched.

**Redesign, same day: per-stage approval gates, PR created early.** The single end-of-pipeline approval gate from Phase 1 was replaced with one gate per stage in the original design doc's diagram, and the pull request now gets created right after tests pass — before review, not after — with review Agent findings pushed as follow-up commits to that same PR. This is a deliberate move to match the design doc's own lifecycle diagram (Section 2) exactly, and to close the very gap the diff-view fix above was patching: more checkpoints where a mistake can be caught before it goes further.

New flow: `plan` → **approve** → `code` (writes the file) → **approve** → `test` (runs it for real) → **approve** → `publish` (creates the branch + PR on approval #1, or pushes a follow-up commit to the *same* branch on any retry) → `review` (runs automatically — an AI reading a PR doesn't need permission) → if `CHANGES_REQUESTED` and under the round cap, back to `code` for another approve/approve/approve/publish cycle against the same PR; otherwise `finish`, reporting the PR and stating plainly whether review's concerns were ever resolved.

Each declined gate stops the pipeline where it stands, with a message specific to what already happened — nothing was touched (declined at plan), the change is on disk but nothing's committed (declined at code or test), or the existing PR still reflects the previous version (declined mid-retry, after a PR already exists). Every new task run also explicitly resets all of a repo's per-task state first (`classify_intent` in `graph.py`) — without this, LangGraph's checkpointer would let an unrelated later request on the same repo mistake itself for a retry of an old, already-merged PR and try to push a "fix" to it.

Verified against a scratch repo with a real local git remote (a bare repo standing in for GitHub, since testing this needed `git push` to actually succeed — Phase 1/2's "no remote" scratch repos couldn't exercise the post-publish review path at all): all four gates worked with correct per-gate wording; a fresh unrelated second task correctly showed "push a branch and open a pull request" rather than "push this fix" (confirming the per-task reset works); a deliberately broken request pushed a real PR, got `CHANGES_REQUESTED`, looped back, and — notably, unlike Phase 2's earlier test — the model actually fixed the underlying bug on retry; round 2 then correctly flagged that the *fix*, while passing tests, no longer matched the original (deliberately bad) request to make `add` multiply — a genuinely correct, nuanced catch, not a false positive. Both commits landed on the same branch and PR, confirmed via `git log` on both the local repo and the fake remote.

**Real-world bug found and fixed, same day (again):** with per-stage gates live, replying to an approval prompt with a genuine new instruction instead of "approve" or "no" — e.g. "make the changes in login.css as well for the email field" — silently discarded the request. Every gate only checked whether the reply was in a small affirmative-word set; anything else was treated as a flat decline, and the actual text was never looked at again.

Fixed in `backend/app/main.py`: `_looks_like_new_instruction()` treats a non-affirmative reply that also isn't a short, plain rejection (no/stop/cancel/etc.) as a real follow-up request rather than a "no." The pending change is still declined first — the graph is never nudged into treating ambiguous text as a "yes," that stays a hard rule — but then, in the same response, a *second* graph invocation starts the new request immediately, and the reply makes clear both things happened: `"(Stopped the previous change — starting this instead.)"` followed by the new plan-approval prompt.

Verified against a scratch repo: at the test-approval gate, replying "make the changes in app.py as well for a divide function" correctly declined the pending change (no branch created, the prior edit stayed on disk uncommitted) and immediately opened a plan-approval prompt for the divide function in the same reply. A plain "no" on a separate run was confirmed to still behave exactly as a simple decline, with no false redirect.

### Phase 3 — Release Readiness + local Docker build — **done**
Two new nodes after `review` approves (not after the round cap with unresolved concerns — that path still ends at `finish_unresolved`, honestly, without pretending readiness scoring happened for a change review never actually approved):

`release_readiness` is **deterministic, not an LLM guess** — the score is built only from signals ReleaseForge AI actually has: tests passed (+50), review approved (+40), review risk Low/Medium/High (+10/+5/+0). It explicitly does not claim to have run a security scan, dependency check, or infrastructure check, because none of those exist yet — matching the capability-honesty principle from Phase 0's system prompt. A GO/NO-GO threshold (≥70) mirrors the design doc's Section 3.6 example output, but every point is traceable to a real check, not synthesized by a model.

`await_readiness_approval` — the fifth approval gate — shows the score, breakdown, and recommendation, and asks to proceed to build. Declining leaves the PR exactly as it is. Approving runs `build_docker_image`: generates a Dockerfile via LLM if none exists (based on the repo's file listing), **pushes it as a new commit to the same PR** rather than leaving it untracked, then attempts `docker build` — checking for `docker` on PATH first and failing with a clear message instead of a crash if it's missing, the same defensive pattern already used for the missing `gh` CLI.

**Docker Desktop turned out not to be installed on this machine at all** (an earlier note assumed it was, just not on PATH — that was wrong). Built and tested accordingly: verified end-to-end against a scratch repo with a real remote — tests passed → review approved → readiness scored `100/100, GO` (50 + 40 + 10, correctly broken down) → approved → a real, sensible Dockerfile was generated and committed as a new commit on the existing PR branch (confirmed via `git log` on both the repo and the remote) → the actual `docker build` call failed gracefully with "Docker isn't installed, or `docker` isn't on PATH" instead of crashing. The one thing that couldn't be verified is a real image actually building successfully — that needs Docker installed, which the user has deferred for now.

### Phase 4 — Deployment Strategy + local Kubernetes + Validation/Monitoring/Recovery — **done**
Rolling/Blue-Green/Canary/Recreate strategy selection, a real deploy to a local `kind` cluster, rollout validation, a short monitoring poll, and rollback-on-failure with an LLM-written root-cause summary.

**Unblocked by the user installing Docker Desktop** (needed a real UAC click no automated session can provide — see the earlier blocked note). Getting there also needed two WSL2 prerequisite fixes first (the `VirtualMachinePlatform` Windows feature wasn't enabled; then the WSL2 kernel file was missing, fixed by `wsl --update`), and `kind` had to be (re-)installed via `winget` from the user's own terminal — it silently failed every time it was attempted from this session's sandboxed shell, a sandbox restriction rather than a real problem with the package. `kubectl` turned out to already be bundled with Docker Desktop (`resources\bin\kubectl.exe`).

Extends the graph past `build_docker_image`, which is no longer terminal: `select_deployment_strategy → await_deploy_approval (gate 5) → deploy → validate → monitor → promote_and_finish`, with `recovery → await_rollback_approval (gate 6) → rollback` as the failure branch off either `deploy`, `validate`, or `monitor`.

- `select_deployment_strategy()` in `graph.py` — **deterministic, same principle as `release_readiness()`**: no existing deployment for this app yet → `Recreate` (nothing to roll from or run a canary against); otherwise Low risk → `Rolling`, Medium → `Canary`, High → `Blue-Green`. A wrong deployment-strategy guess has real consequences (downtime, half-served traffic), so this is read from real signals (review risk, readiness score, whether the app has a prior deployment), never an LLM's judgment call.
- `backend/app/agents/k8s_tools.py` — new module, same shape as `tools.py`: sandboxed, synchronous, subprocess-based wrappers around `kind`/`kubectl`, called via `asyncio.to_thread` from the async nodes. Manifests (Deployment + Service) are built as plain Python dicts and serialized with `pyyaml` — **deterministic, not LLM-generated**, unlike the Dockerfile in Phase 3: a malformed or wrong Kubernetes manifest is a cluster-changing mistake, not a code-review-catchable one.
- **Recreate/Rolling** map directly onto Kubernetes' own native `Deployment.spec.strategy.type` — no extra machinery needed.
- **Blue-Green** is real, not simulated: a second Deployment (`<app>-<color>`) is created and validated *before* any traffic reaches it; only on success does `promote_and_finish()` patch the Service's selector to the new color and remove the old one. A failed Blue-Green deploy never touched live traffic in the first place — rollback there just means deleting the untested side.
- **Canary** is also real, via the simplest honest technique available without a service mesh: a second Deployment (`<app>-canary`) with fewer replicas sits behind the *same* Service as the stable Deployment (both share the `app` label; only a `version` label differs), so Kubernetes' own Service load-balancing naturally splits traffic roughly by replica ratio. No fine-grained percentage control (that needs Istio/Linkerd-class tooling this project doesn't have), and that limit is stated here rather than implied to be more than it is.
- `recovery()` — the one LLM call in this whole extension: reads `kubectl logs` + `kubectl describe pods` and writes a short, plain-English root-cause summary, shown alongside the rollback approval prompt (gate 6) rather than a raw log dump.
- `rollback()` — strategy-aware: Recreate/Rolling get a real `kubectl rollout undo`; Blue-Green/Canary just delete the untested side, since neither ever put the new version in the live traffic path to begin with.

**Verified live, not just unit-tested — and it's exactly what caught four real bugs unit tests couldn't have.** With Docker/kind/kubectl actually working, a throwaway scratch app (a two-line Python HTTP server) was built into a real image and run through `deploy → validate → monitor → promote_and_finish` for all four strategies in sequence against the real cluster, plus a deliberate failure (a nonexistent image tag) through `recovery`/`rollback`. Bugs found and fixed, in the order they surfaced:

1. **A genuine environment problem, not a code bug:** the first live run crashed with a Windows console `UnicodeDecodeError` reading `kind`'s progress output (it prints unicode checkmarks that aren't valid cp1252, Windows' default console encoding) — `_run()` in `k8s_tools.py` now decodes as explicit `utf-8` with `errors="replace"`, matching the same reasoning `tools.py`'s `read_file()` already used.
2. **A second genuine environment problem:** every `kubectl` call then failed with `x509: certificate signed by unknown authority`. Inspecting the actual TLS certificate the API server presented showed the real cause: **Avast's Web/Mail Shield was intercepting HTTPS on `127.0.0.1`**, re-signing the kind cluster's own certificate with an Avast-generated one that `kubectl`'s pinned CA correctly rejected — almost certainly the same interception layer behind the `pip install` SSL errors earlier in this project. Fixed by the user excluding local traffic from Avast's HTTPS scanning; nothing in this codebase could have worked around it.
3. **A real bug in this code:** `build_deployment_manifest()` was labeling Blue-Green/Canary pods with `app=<the deployment's own resource name>` (e.g. `app=myapp-green`) instead of `app=<the shared app name>` (`app=myapp`). The Deployment itself still worked (its internal pod-selector is self-consistent regardless of the label's actual value), which is exactly why this didn't show up as an obvious crash — `monitor()`'s pod-restart check just quietly reported "no pods matched," and the Service selector patch during promotion would have matched zero real pods. Fixed by explicitly passing the shared `app_name` inside `extra_labels`, which is allowed to override the default. Locked in with a regression test.
4. **A second real bug, found by reasoning through the endpoint IPs the live run printed:** `patch_service_selector()` used `kubectl patch --type=merge` — a JSON Merge Patch, which recursively merges nested objects rather than replacing them. Patching selector `{"app": "x"}` onto a live selector of `{"app": "x", "version": "green"}` left `"version": "green"` sitting there untouched, since merge patch only overwrites keys it names. A Canary deploy run right after a Blue-Green promotion kept routing only to the promoted color — the canary pod never received any traffic at all, silently. Fixed by switching to a JSON Patch **replace** operation (`--type=json`, `{"op": "replace", "path": "/spec/selector", ...}`), which swaps the field wholesale. Also locked in with a regression test.
5. **A third real bug, downstream of #4:** `promote_and_finish()`'s Canary branch assumed a plain-named stable Deployment (`<app>`) always exists to promote into, and unconditionally deleted the canary Deployment regardless of whether that promotion actually succeeded. When the app's current stable version was actually deployed under Blue-Green naming (`<app>-green`), the promotion attempt failed — and the canary got deleted anyway, destroying real, currently-serving capacity for a promotion that never happened. Fixed to check `deployment_exists()` for real and, when there's nothing safe to promote into, leave the canary running rather than delete it.

After all five fixes, the same live sequence produced strictly correct, independently-checked results: a real `kubectl get endpoints` inspection (not just "the command exited 0") confirmed 2 real pod IPs after Recreate, the *same* 2 after an idempotent Rolling redeploy, 2 *new* IPs after Blue-Green actually switched traffic to the promoted color, and — the concrete proof strategy-mixing now works — **3** IPs after Canary (2 stable + 1 canary, the expected replica-ratio split), with the canary correctly left running since no plain-named stable Deployment existed to promote it into. The failure path was verified too: a deliberately nonexistent image tag failed to apply, and `rollback()` correctly reported nothing further to undo (the failed deploy never touched anything to roll back).

**A known, stated limitation, not silently papered over:** a full N×N matrix of strategy-to-strategy transitions (e.g. Canary immediately after Blue-Green, which the live test exercised and fixed) isn't exhaustively handled — "promote into the stable version" currently has one real code path (a plain-named Deployment) and one honest fallback (leave the newer side running rather than delete real capacity for a promotion it can't safely perform). A fuller fix would need this tool to track "what is this app's currently-promoted deployment" as its own piece of state, rather than inferring it purely from Kubernetes resource names — a reasonable next increment, not something this phase claims to have solved completely.

Not built in this phase: `minikube` as an alternative to `kind` (redundant — `kind` alone is enough to teach the concept), and true fine-grained canary traffic percentages (needs a service mesh this project doesn't have and doesn't currently need).

### Phase 5 — Memory layers (SQLite for now, Postgres was the plan) — **done**
Skipped ahead of the blocked Phase 4, at the user's direction — there's already real release history from Phases 1–3 to store, even without Phase 4's deployment/incident data. **Postgres isn't installed either, and there's still no Docker to containerize it**, so this phase was built on SQLite instead, deliberately: SQLAlchemy (async, via `aiosqlite`) means swapping to real Postgres later is a connection-string change in `backend/app/memory/db.py`, not a rewrite — the same swappability principle the `LLMProvider` interface already established for models.

**This phase exists because of a real incident.** A live approval got interrupted mid-flow by an unrelated backend restart (my own scratch-repo testing on the same port as the user's live session — a mistake, now fixed by testing on a different port going forward) and the in-progress change was lost, exactly the failure `MemorySaver`'s docstring had already predicted back in Phase 1. Fixing that for real was this phase's actual center of gravity:

- **Conversation/approval memory**: LangGraph's `MemorySaver` (in-memory, gone on restart) is replaced by `AsyncSqliteSaver` (`langgraph-checkpoint-sqlite`), opened once in FastAPI's `lifespan` and stored on `app.state.graph` instead of the old module-level singleton. A genuinely open, currently-actionable gap, not a hypothetical one.

  **A real bug found and fixed during a follow-up documentation audit, not by a test:** `_maybe_record_release()` calls `await memory.record_incident(...)` *before* `/chat` returns its already-fully-computed reply, and — unlike the `ingest_incident_record()` call two lines below it — the write itself wasn't wrapped in `try/except`. A SQLite write failure on a rollback outcome (locked file, full disk, anything) would have raised straight through `/chat`'s handler and turned into a 500, discarding a reply the user should have gotten regardless of whether incident-memory bookkeeping succeeded. Fixed by wrapping the persist-and-ingest pair as one best-effort block, matching the same non-fatal reasoning already applied to RAG ingestion everywhere else — `record_release()` itself, a few lines up, is deliberately left unwrapped, since every outcome already depends on it succeeding and it's the one write actually worth failing loudly for. Caught by re-reading the new code path end to end while writing this addendum, not by a regression test — this project still has zero `TestClient`-based tests for any FastAPI endpoint (see the gap audit below), so nothing would have caught this automatically.

**A second, more serious real-world bug, found right after: the backend could freeze entirely, indefinitely, on a real `git push`.** Every scratch-repo test in this project pushed to a local `file://` remote, which never needs authentication — so a critical gap went uncaught until a real push to GitHub hit it. `_run_git()` in `tools.py` never closed stdin and never set a timeout; if `git push` needed credentials, it would try to prompt for them — but the backend has no terminal attached (it's spawned headlessly by the extension), so the prompt would just hang forever, waiting on input that could never arrive. Because that blocking call ran directly inside an `async def` node with nothing offloading it, it froze Python's single-threaded event loop completely — not just that one request, *every* request, including `/health` — which is exactly why the extension reported "fetch failed": the backend wasn't down, it was just permanently stuck.

Two fixes, addressing both the trigger and the blast radius:
1. Every subprocess call in `tools.py` (git, tests, `gh`, `docker`) now passes `stdin=subprocess.DEVNULL`, so a credential prompt can never even try to appear — git's own credential helpers fail fast and cleanly instead of hanging. `_run_git()` also gained a hard 60s timeout as a backstop for any hang that isn't a credential prompt.
2. Every git/test/Docker call in `graph.py`'s async nodes (`test`, `publish`, `build_docker_image`) is now wrapped in `asyncio.to_thread(...)`, so even a legitimately slow operation runs on a worker thread instead of blocking the event loop — the backend stays responsive to other requests (health checks, a different repo's task) the whole time.

Verified directly: pushing to a real GitHub-shaped HTTPS remote that would need credentials completed (with a clean failure) in 17 seconds instead of hanging forever — the exact scenario that had been silently untested. The full happy path was re-run afterward against a working local remote to confirm the `asyncio.to_thread` wrapping didn't change any actual behavior, only where it runs.

### Phase 6 — RAG + Knowledge Graph — **done**
Retrieval over the release records Phase 5 generated, plus the project's own two design docs, grounding chat answers instead of the model guessing from training data alone.

**This machine still has no Docker** (see Phase 4's blocker, unchanged), so Qdrant and Neo4j — the doc's Section 5/8 picks — aren't options here either. Same swap-later principle as Phase 5's SQLite standing in for Postgres: `backend/app/rag/vector_store.py` wraps **Chroma in embedded/persistent mode** (a local directory, no server process) instead of Qdrant, and `backend/app/rag/graph_store.py` is a **plain nodes/edges schema on SQLite** instead of Neo4j/Cypher. Both are isolated behind small interfaces (`VectorStore`, `GraphStore`) specifically so a real Qdrant/Neo4j deployment later is a swap inside one module, not a rewrite of anything that calls them.

What got built:
- `backend/app/rag/chunking.py` — splits markdown on its own headings (not a fixed-size sliding window), further wraps any section still too long on paragraph boundaries; one `ReleaseRecord` becomes one chunk (already small, splitting further would just fragment one fact). Chunk ids are content-addressed (`sha256` of the text) — re-ingesting an unchanged doc on every backend restart upserts the same ids instead of duplicating.
- `backend/app/rag/vector_store.py` — Chroma wrapper; `add()`/`query()`/`get_all()`.
- `backend/app/rag/keyword_store.py` — BM25 (`rank_bm25`) over whatever `get_all()` returns, rebuilt per query rather than kept as a second standing index that has to stay in sync with Chroma's.
- `backend/app/rag/retriever.py` — `hybrid_retrieve()`: dense (embedding) + sparse (BM25) results merged by **reciprocal rank fusion**, not just dense alone — dense catches paraphrases, sparse catches exact identifiers (a file path, a branch name) dense embeddings tend to blur. This is the actual "hybrid retrieval" concept from the design doc's Section 7 pipeline, not a dense-only stand-in for it.
- `backend/app/rag/graph_store.py` — `Application -[HAS_RELEASE]-> Release -[MODIFIED]-> File`, `Application -[HAS_FILE]-> File`, built from real `ReleaseRecord` rows. Answers "which releases touched `login.py`" today; still a small fraction of the design doc's fuller `Application -> Service -> API -> Database -> Deployment -> Incident` chain, since those extra node types don't exist as data anywhere yet.
- `backend/app/rag/ingest.py` — `ingest_project_docs()` (idempotent via a content hash — an unchanged doc costs zero embedding calls on the next restart) and `ingest_release_record()`, called automatically: docs once at startup (`main.py`'s `lifespan`), each release record immediately after `record_release()` persists it.
- `LLMProvider.embed()` — new method on the provider interface (`base.py`), implemented in `OllamaProvider` against a **separate embedding model** (`nomic-embed-text` by default, `RELEASEFORGE_EMBEDDING_MODEL` to override) — a chat-tuned model isn't also an embedding model, so this needs its own `ollama pull`.
- `chat_reply` in `graph.py` — the CHAT path now retrieves before answering: top hybrid hits plus recent graph relationships get folded into the system prompt with source tags, so "what changed in my last release" or "what's DeployGenie's build philosophy" can be answered from real indexed history instead of the model's guess.

**Deliberately non-fatal everywhere.** RAG depends on Ollama actually running with the embedding model pulled — nothing here can be assumed available. Doc ingestion at startup, release-record ingestion after each task, and retrieval before a chat reply are each wrapped so a failed embedding call is caught, logged, and produces an empty/no-context result — never a crashed startup or a broken chat turn. `chat_reply` without any retrieved context behaves exactly as it did before this phase.

### Phase 7 — MCP-ify the tool layer — **done**
Retrofit the ad-hoc git/docker/k8s calls from Phases 1–4 into proper MCP servers plus one MCP client. Deliberately late: by now it's clear exactly what each agent needs, so wrapping it in MCP teaches what the protocol actually buys (tool discovery, permissioning, multi-server orchestration) instead of building ceremony around tools that don't exist yet.

**SDK note, since the design doc explicitly says to verify this before writing MCP code:** the installed `mcp` package is version **2.0.0**, not the older `FastMCP`-branded 1.x API most MCP tutorials still show. The high-level server class lives at `mcp.server.mcpserver.MCPServer` (not `mcp.server.fastmcp.FastMCP`, which doesn't exist in this version) — same decorator-based `.tool()` shape, just renamed and reorganized. Confirmed by importing the package fresh and inspecting its actual module layout and class signatures rather than assuming from memory.

**Three MCP servers, one client, real multi-server orchestration:**
- `backend/app/mcp_servers/filesystem_server.py` — file read/write, git commit/push, PR creation, test detection/running (11 tools). Thin wrappers around `app/agents/tools.py`, which still owns the actual logic — MCP-ifying this is about *how the agent graph reaches these operations*, not a rewrite of what they do.
- `backend/app/mcp_servers/docker_server.py` — `run_docker_build` (1 tool), its own process on purpose: real multi-server routing (a `write_file` call goes to a different server than a `run_docker_build` call, transparently) and the design doc's Section 14 "give an agent only the tools it needs" principle — a Coding Agent that only needs filesystem+git tools has no reason to also hold a live handle into the Docker socket.
- `backend/app/mcp_servers/kubernetes_server.py` — the real, subprocess-touching parts of `k8s_tools.py` (14 tools: `ensure_kind_cluster`, `apply_manifests`, `patch_service_selector`, `rollout_status`, ...). Deliberately does **not** expose the pure, no-subprocess helpers (`build_deployment_manifest`, `decide_deployment_strategy`, `sanitize_dns_label`, ...) as MCP tools — those aren't actions on an external system, they're plain application logic that happens to live next to the real tools, same reason a filesystem server wouldn't expose "capitalize this string" as a tool.
- `backend/app/mcp/client.py` — `MCPClientManager`: spawns all three servers as real subprocesses (`python -m app.mcp_servers.X`, `cwd` pinned to `backend/`), does a real MCP handshake with each, and — this is the actual "tool discovery" concept, not a lookup table with extra steps — calls `list_tools()` on each server and builds its own tool-name → server-name routing index from what the servers actually report, rather than a hardcoded mapping. `call_tool(name, args)` looks up the owning server and routes there.
- `backend/app/mcp/factory.py` + `main.py`'s `lifespan` — the client starts once at backend startup (spawning the three subprocesses) and stops on shutdown, the same "open expensive resources once" pattern the LangGraph checkpointer and RAG stores already established. Verified directly: a full `TestClient` app boot/shutdown cycle leaves zero orphaned Python processes behind.

**`graph.py` retrofitted end to end** — every node from Phase 1 through Phase 4 that used to import `tools.py`/`k8s_tools.py` directly (`plan`, `code`, `test`, `publish`, `build_docker_image`, `select_deployment_strategy`, `deploy`, `validate`, `monitor`, `promote_and_finish`, `recovery`, `rollback`) now calls `get_mcp_client().call_tool(...)` instead. `graph.py` no longer imports `tools.py` at all. A genuine side benefit, not just an architectural nicety: every `asyncio.to_thread(...)` wrapper that Phase 5 had to add around a blocking git/docker/kubectl subprocess call is now unnecessary and has been removed — the real subprocess work happens inside the MCP server's own separate process now, so awaiting an MCP call from this backend is just waiting on a pipe read, which was never a blocking operation to begin with.

**A real SDK quirk found and worked around, not glossed over:** this `mcp` version doesn't reliably populate `CallToolResult.structured_content` for a tool whose return type is annotated as a plain `dict` — confirmed directly: it did populate `structured_content` for `list`/`str`/`bool` returns, not for `dict`. `MCPClientManager` (via a shared `extract_tool_result()` function, also used directly by the test suite) falls back to parsing the tool's text-content block as JSON in that case, so every caller gets back a real Python value either way rather than needing to know which return shape happened to get the structured treatment.

**Verified live against real subprocesses, not just protocol-level unit tests:**
- A full scratch git repo with a real local bare remote, exercising `write_file`, `read_file`, `commit_and_push`, `push_fix_commit`, and `open_pull_request` through the filesystem MCP server — including confirming `open_pull_request` still degrades gracefully (no `gh`, no github.com remote) through the MCP layer exactly as it did calling `tools.py` directly.
- A real Docker build through the docker MCP server (`releaseforge-phase4-scratch:v1`, the same scratch app from Phase 4's live verification).
- The **entire Phase 4 deploy pipeline re-run through the MCP-routed `graph.py` functions** (not the old direct `k8s_tools` calls) — `deploy → validate → monitor → promote_and_finish`, plus the deliberate-failure → `rollback` path — against the real `kind` cluster, with the same `kubectl get endpoints` check from Phase 4 confirming real pod IPs were actually being served, not just that commands returned success. Nothing broke in the retrofit; the exact same strategies that worked live in Phase 4 still work live, now routed through three subprocesses and a JSON-RPC protocol instead of plain function calls.

**Also added:** `backend/tests/test_mcp_servers.py` — 9 fast, repeatable protocol-level tests using the MCP SDK's own `InMemoryTransport` (a genuine `ClientSession` ↔ `MCPServer` round trip, tool registration and JSON schema validation included, just without a subprocess) — covering tool registration for all three servers, a real write/read round trip, the missing-file and missing-Dockerfile graceful-failure paths, and confirming `tools.py`'s path-sandboxing still rejects a directory-escape attempt through the MCP layer exactly as it did before this phase.

Not built in this phase: MCP `Resources` and `Prompts` (only `Tools` — the concept these servers actually needed), and auth/permission scoping on top of MCP itself (Phase 9's job, per the design doc's own Section 14 sequencing).

### Phase 8 — Observability + Evaluation — **done**
OpenTelemetry traces, token/cost tracking, task success rate, review acceptance rate, deployment success rate — instrumenting a system that's now stable enough to be worth watching.

**Docker being unblocked (Phase 4) changed what this phase could honestly be.** Every earlier phase that wanted real infrastructure (Postgres, Qdrant, Neo4j, a trace collector) had to substitute an embedded/local stand-in because there was no Docker to run anything in. That's no longer true here — this phase runs a real **Jaeger** container (`jaegertracing/all-in-one`, via `docker run -d --name releaseforge-jaeger -p 16686:16686 -p 4318:4318 jaegertracing/all-in-one:latest`) as a real OTLP trace collector, and traces were verified landing in it for real, not console-printed as a stand-in. **Tracing (`backend/app/observability/tracing.py`):**

A genuine bonus found along the way: the MCP SDK itself is already OTel-instrumented internally (`MCP send initialize`, `MCP send tools/call ...` spans appeared automatically, riding the same global TracerProvider) — richer traces than what was explicitly written, for free.
- **Workflow-level** (`main.py`) — a `workflow.chat` span wraps the whole `/chat` handler (workspace path, resumed/redirected/interrupted flags, final outcome), plus `FastAPIInstrumentor.instrument_app(app)` for automatic HTTP request spans on every route — the design doc's "workflow duration" starts at the HTTP boundary, not just inside the agent graph.

A second live check confirmed real MCP tool-call spans (`mcp.call_tool.has_dockerfile`, `mcp.call_tool.deployment_exists`) landed with the right `mcp.tool_name`/`mcp.server_name` attributes. LLM-call span attributes (token usage) are code-complete but not live-verified — this environment still has no Ollama running, the same gap Phase 6 already documented honestly.

**Evaluation (`backend/app/eval/`) — design doc Section 16, computed from real history, not simulated:**
- `metrics.py` — `AgentMetrics` (completion rate, outcome breakdown), `CodingMetrics` (test pass rate, review acceptance rate, average readiness score), `DeploymentMetrics` (success rate, rollback rate, broken down by deployment strategy), all computed from real `ReleaseRecord` rows via a new `GET /eval/summary` endpoint. Every rate is **`None`, not a fake `0.0` or `100%`, when there's no data yet** — there's a real difference between "0 of 0 attempts succeeded" and "10 of 10 failed," and collapsing that distinction would be exactly the kind of dishonest metric this project has avoided everywhere else.
- **A real gap found and fixed while building this:** `ReleaseRecord` never actually stored which deployment strategy a release used, even though Phase 4 fully implemented four of them — `_maybe_record_release()` in `main.py` just never captured that field. Added `deployment_strategy` to the `ReleaseRecord` model and started populating it. No migration tooling exists (no Alembic) — an existing `data/memory.db` from before this phase needs a fresh database to pick up the new column, stated plainly rather than silently broken.
- Not included, and stated honestly rather than faked: **planning accuracy / tool selection accuracy** (no ground-truth labels exist for "was that the right file/tool"), **regression rate** (no notion of "this release broke something a prior one didn't"), **mean time to recovery** (`ReleaseRecord` stores one row per finished task, not separate failure/recovery timestamps to compute a duration from).
- `rag_eval.py` — Precision@k, Recall@k, Mean Reciprocal Rank, and binary-relevance NDCG@k, as pure functions (ranked ids in, a number out) plus an `evaluate_retrieval()` harness that runs Phase 6's real `hybrid_retrieve()` against a set of real `EvalQuery` examples. **Faithfulness is not included** — that needs an LLM judging whether a generated *answer* is actually supported by retrieved text, a different kind of evaluation (answer quality, not retrieval quality) than this module attempts. The metric functions are unit-tested directly (17 tests, no embedding model needed); `evaluate_retrieval()` itself needs a reachable embedding model to run for real, the same Ollama-shaped gap as everywhere else RAG shows up in this environment.

  **Addendum — now built, and directly motivated by a real failure this project produced itself.** The Phase 6 addendum below records a live chat answer that correctly cited real retrieved text and still misstated one fact from it — reporting "Qdrant" when the retrieved passage said Chroma had replaced Qdrant. That's exactly the retrieval-was-right-but-the-answer-still-drifted gap this module's own docstring used to say it didn't attempt. `judge_faithfulness(llm, question, answer, passages)` now exists: an LLM-as-judge prompt asking specifically for claims the passages don't support (including ones they contradict, not just ones they never mention), parsed the same tolerant way `graph.py`'s `classify_intent`/`review` nodes already parse LLM JSON output — a malformed judge response is treated as `faithful: False`, not silently passed through, since a check that no-ops on its own failure is worse than no check. Wired into a new `POST /eval/faithfulness` endpoint that re-retrieves the same passages `chat_reply()` would have used for a given question, then judges a given answer against them — checking a real answer against real retrieval, not a fabricated pair.

  **Live-verified, with an honest, useful nuance.** Hitting the endpoint with the original question and the exact real answer that shipped came back `faithful: true` — at first glance a miss, until checking *what it actually retrieved*: the vector store's content has changed since the original test (the build plan doc has been edited repeatedly since, changing its content-addressed chunk ids), so the specific "Chroma replaced Qdrant" passage no longer ranked in the top 4 for that question — the endpoint correctly judged faithfulness against what it was actually given, which is a real, honest property of a system whose corpus keeps changing, not a defect in the judge. Controlling for that by calling `judge_faithfulness()` directly with the exact real passage that caused the original mistake: **it correctly returned `faithful: false`, flagging `"The hybrid retrieval approach used Qdrant as the vector database"` as unsupported, with the correct explanation** ("the passages indicate... Chroma is used instead"). A second check — the same question, a corrected answer using Chroma, but only that one narrow passage — also came back `faithful: false`, for a different and equally correct reason: that single sentence doesn't mention BM25 or reciprocal rank fusion at all, so the judge correctly refused to bless a claim the passage it was given genuinely doesn't support, rather than assuming background knowledge. Both real Ollama calls, ~90–130s each on this machine's CPU-only inference.

### Phase 9 — Security hardening — **done**
RBAC, per-agent tool scoping (per the design doc's Section 14 table), secrets management, audit logs — retrofit onto a stable agent/tool graph rather than guessing permission boundaries upfront.

**What "RBAC" honestly means here.** The design doc's Section 14 also lists OAuth/OIDC and user-level RBAC — those don't apply to this project as it exists today: it's a single local backend behind one VS Code extension, with no second user to scope access away from. Building OAuth for a tool with one user would be security theater, not hardening. What genuinely applies, and is genuinely enforceable, is the design doc's own framing one line later — "Agents should have only the tools they need" — read literally: **least-privilege scoping of which MCP tools each agent role can invoke**, regardless of who's asking.

- `backend/app/security/scopes.py` — `ROLE_SCOPES`, mapping six roles (`coding`, `test`, `publish`, `build`, `deployment`, `recovery` — this project's actual graph-node groupings, not the design doc's more abstract agent names) to the exact MCP tools each one may call. `deployment` and `recovery` both include `delete_deployment` deliberately — the same tool, two legitimate purposes (post-promotion cleanup vs. rollback-by-deletion) — but `deployment` cannot reach `pod_logs`/`describe_pods`/`rollout_undo`, and `recovery` cannot reach `apply_manifests`/`patch_service_selector` — a Recovery Agent has no business deploying anything new. An unknown role **fails closed**, not open.
- Enforced **client-side**, in `MCPClientManager.call_tool()` — not inside the MCP servers themselves. These servers only ever talk to this one trusted local client over stdio pipes, never a network an untrusted client could reach; the design doc's "network isolation" is already true by construction here, so a second server-side auth layer would just re-check the same fact twice. `call_tool()` now takes `role` as a **required** argument — every one of graph.py's 41 call sites had to be updated to declare its role explicitly, so a new call site can't quietly go unscoped just because nobody thought to add the argument. Verified with an automated cross-check: every `(role, tool)` pair actually used in `graph.py` was checked against `ROLE_SCOPES` and confirmed permitted, catching a mapping mistake before it could ever surface at runtime.
- `backend/app/security/secrets.py` — refuses to read conventionally secret-shaped files (`.env`, `*.pem`, `id_rsa`, credential JSON, ...), enforced inside `filesystem_server.py`'s `read_file` tool. The real risk this closes isn't "someone reads your `.env`" (anyone with filesystem access already can) — it's that `read_file`'s content gets embedded straight into an LLM prompt (`code()`'s "current file contents") or an API response; a task that innocently says "update the config" should never cause a real API key to end up in a chat transcript. `.env.example`/`.env.sample`/`.env.template`/`.env.dist` are deliberately exempted — real, widely-followed placeholder-only conventions, and refusing them would block an entirely ordinary task for no safety benefit.
- `backend/app/security/audit.py` + a new `AuditLog` table — one row per MCP tool call attempted, whatever the outcome (`ok` / `error` / `scope_denied`), surfaced via `GET /audit/log`. A scope-denied attempt is exactly the kind of event an audit log exists to catch, so it's logged too, not silently swallowed as a Python exception.

**Two real bugs found by live verification, not by unit tests alone:**
1. **A genuine security gap in the secrets guard itself.** The first live run tried to read a file named `_fake_secret_for_test.env` — and it sailed straight through unrefused. The pattern list only caught the dotfile-prefix convention (`.env`, `.env.local`) and missed the equally common suffix convention (`production.env`, `local.env` — no leading dot at all). Fixed by adding a `*.env` suffix pattern; a regression test locks in the exact filename that exposed it.
2. **A test-methodology bug, not a product bug, but worth recording:** the first live-check script mixed `TestClient`'s own event-loop management with a separate `asyncio.run(...)` for the actual MCP calls — and the real subprocess call hung indefinitely, because the MCP client's stdio streams were bound to a different event loop than the one trying to await them. Diagnosed by isolating the audit-log DB write alone (it returned instantly — not the cause) and then recognizing the mismatch. Fixed by following the same pattern Phase 7/8's own live checks already used successfully: call `start_mcp_client()` directly inside one `asyncio.run(...)`, never through `TestClient`'s wrapper. A reminder that testing async subprocess-backed code has its own sharp edges, distinct from testing the code's actual logic.

**Verified live, end to end, against real subprocesses and a real database** (not mocked): an allowed call (`coding` → `read_file`) succeeded: a denied call (`coding` → `delete_deployment`) was rejected before it ever reached the underlying MCP session; the secrets guard refused a real sensitive file through a real subprocess round trip; and `GET /audit/log`-equivalent queries returned all three real events, correctly classified as `ok`, `scope_denied`, and `error`.

Not built in this phase: OAuth/OIDC and user-level RBAC (no second user exists to scope away from — see above), MCP server-side authorization (redundant given the trusted-local-client architecture), and network/container isolation as a distinct control (already true by construction: MCP servers are stdio subprocesses with no listening port, and the only network-exposed process is the FastAPI backend itself, unchanged from every earlier phase).
